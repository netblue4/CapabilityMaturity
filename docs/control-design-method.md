# How we design controls

This explains the method behind the **Operationalise** prompt (`docs/control-coverage-prompt.md`) — the house standard for writing a control, and how the same method runs in the **two scenarios** you actually face:

1. **Brand‑new control** — you've mapped the policy & group‑standard statements, but there is no existing control yet.
2. **Rewrite an existing control** — you've mapped the statements *and* you already have a control (the scenario the prompt is built for).

The destination is the same in both: **two documents** to the house standard — **the control** (for the owner) and **the CSA test** (for the tester). What differs is the *starting material* and therefore how much the prompt **reuses** versus how much it **proposes**.

---

## The house standard (the rules both scenarios obey)

1. **A control is an assurance activity — the *checking*, not the *doing*.** The business process (log the incident, patch the server) is not the control; the review / approval / reconciliation / monitoring *over* it is. Name the control by its type (4‑eye check, reconciliation, approval, dashboard monitoring…).
2. **Two documents, two readers.** *The control* tells the owner what to do; *the CSA test* tells the tester how to obtain the evidence and check it. They are separate — the test is CSA documentation, not part of the control.
3. **Evidence is generated by the control, obtained by the test.** Every evidence‑producing **Control Step saves a NAMED artefact** (`"<Evidence Name> – <id>"`). The name is the **join key**: Control Step → Control Evidence list → the test check that reads it by the same name.
4. **Never invent — mark it.** Anything the inputs don't give (a URL, a threshold, a system, a seniority, a path, a timing) becomes a clearly‑named placeholder `[@snake_case_description]` for the owner to complete in review.
5. **Readiness gate (soft).** A control is "ready" when every gap is an explicit placeholder (clearly marked), not when every value is filled.

And the prompt always runs as a **two‑step dialogue**, never one‑shot:

- **STEP 1 — Reason & propose.** It walks the derivation (statements → what assurance is needed → process vs control → classification → the split) and proposes a **control set** (one row per resulting control), then **stops** for your confirmation.
- **STEP 2 — Build.** Once you confirm, it writes DOCUMENT A (the control) and DOCUMENT B (the CSA test) for each agreed control, plus a coverage check and the readiness gate.

---

## The one thing that changes between the two scenarios

The whole method hinges on one question: **where do the operational specifics come from?**

| | Brand‑new control | Rewrite an existing control |
|---|---|---|
| **Inputs** | Mapped statements only | Mapped statements **+ the existing control text** |
| **The control is…** | **designed** from what the statements require | **reframed** from what the existing control already does |
| **Specifics (systems, tools, URLs, role, frequency, evidence path)** | Not supplied → almost all become `[@…]` placeholders (or a clearly‑marked *proposed* default) | **Reused** from the existing control and folded into the steps; only the true gaps become `[@…]` |
| **Main risk** | An empty skeleton, or inventing specifics that aren't real | Mis‑identifying the process as the control (or vice‑versa) |
| **Placeholder density** | **High** — that's correct, not a failure | **Low‑to‑medium** |
| **In the prompt today?** | No — the prompt expects an existing control; see the adaptation below | **Yes** — this is what the prompt is written for |

Everything else — the house standard, the two documents, named evidence, the classification, the split, the coverage check, the readiness gate — is **identical** in both.

---

## Scenario 1 — Brand‑new control (statements, no existing control)

You have the mapped policy & group‑standard statements and nothing else. There is no process description to reuse, so the prompt must **design the control from the statements' intent**.

**How the method runs:**

1. **Read each statement's intent** — what must be assured (e.g. "P1 incidents are escalated within the agreed timeframe").
2. **Infer the underlying process** the statement governs (the *doing*: incidents are logged, triaged, escalated).
3. **Design the assurance activity** — the check that gives comfort the process happened and was correct. This is the control. Classify it (type / nature / key?) and decide the split (one control, or several by performer / tool / frequency).
4. **Write the control as a skeleton that a first‑time owner can run** — Control Steps that each save a **named** evidence artefact, with every operational specific carried as a placeholder:
   - `[@controller_seniority]`, `[@system_location]`, `[@evidence_folder_path]`, `[@exact_criteria_to_check]`, `[@threshold]`, `[@frequency]` …
   - Where a sensible default exists, it may be offered as **"proposed — owner to confirm"**, but it is never asserted as fact.
5. **Write the CSA test** against those named artefacts, and run the **coverage check** so every mapped statement is assured by at least one step.

**What "good" looks like here:** a well‑shaped, correctly‑classified control whose *structure* is complete and whose *values* are a clean list of placeholders. The readiness gate reads **"Yes — clearly marked"** with a longer `[@…]` list than a rewrite would have. That is the intended output: the prompt has done the design thinking; the owner supplies the facts.

**This scenario is not wired into the prompt.** The prompt appends an existing control under `## CONTROLS TO REVIEW`. To use it for a brand‑new control you have two options:

- **Stub it.** Paste a one‑line "existing control" — just the intended **name + owner + the statements it must satisfy** — and let the prompt treat the rest as gaps (it will fill the structure and mark everything else `[@…]`). This is the quickest route and needs no prompt change.
- **Adapt it.** If brand‑new becomes a regular need, add a short "no existing control — design from the statements" branch to the prompt's derivation (Stage 2 would read "no control exists; design the assurance activity from the statements' intent"). Flag it if you want this built.

## Scenario 2 — Rewrite an existing control (statements + existing control)

You have the mapped statements **and** an existing control (typically pulled from Riskonnect). This is what the prompt is built for, and the transformation is the heart of the method:

> **The existing control's "Description" is usually the *process* (the doing); its "Control Test" is usually the actual *control* (the checking). The fix is to swap them** — the checking becomes the control, and the old test's checks become **Control Steps that save named evidence**.

**How the method runs:**

1. **From the statements** — list what must be assured.
2. **Read the existing control** — decide whether it's really an assurance activity or a process/requirements list.
3. **Separate the process from the control**, classify (type / nature / key?), and decide the split (keep one, or split by performer / tool / frequency).
4. **Write the control** — reuse the existing control's **real specifics** (systems, tools, URLs, documents, role, frequency) and fold them into Control Steps, each ending by saving a named evidence artefact. Tie each step to the statement(s) it assures. Only the genuine gaps become `[@…]`.
5. **Write the CSA test** — Obtain the named evidence (sample) → Check compliance, one `[verifies: <ref>]` per check. Reconcile the test frequency with the control frequency (e.g. a quarterly control sampled 2× a year, not annually).
6. **Coverage check + readiness gate.**

**What "good" looks like here:** the real tools and URLs from your existing control appear *in the steps*; placeholders are confined to the handful of specifics the old control never stated. The readiness gate reads **"Yes — clearly marked"** with a short `[@…]` list.

## Both scenarios produce the same two documents

**DOCUMENT A — THE CONTROL** (for the owner): Control Name (+ type) · Objective · Description (systems + controller seniority) · **Control Steps** (each saves a named artefact) · Frequency · Evidence location + the named Evidence list · linked statements · a supplementary cost line.

**DOCUMENT B — THE CSA TEST** (for the tester): Reviewer / Performer · test method (Inquiry < Observation < Inspection < Reperformance) · sample size (from the RCSA table, by control frequency) · **Obtain the named evidence → Check compliance**, each check reading an artefact **by name** and tagged `[verifies: <ref>]`.

And both end the same way:

- **Coverage check** — every mapped statement is assured by at least one Control Step and tested by at least one check; anything not assured is flagged (add a step, or record it as not controlled).
- **Readiness gate (soft)** — *Clearly marked for a fresh owner? / a fresh tester?* "Yes" means every gap is a named `[@…]`, ready to hand over — not that the values are filled.

---

## Quick reference

**Brand‑new control** → feed the statements (stub a one‑line "control" with name + owner) → Step 1 proposes the control set → confirm → Step 2 builds a structurally complete control with the specifics as `[@…]` placeholders → owner completes the placeholders.

**Rewrite an existing control** → feed the statements + the existing control → Step 1 proposes the shaping (process vs control, type, split) → confirm → Step 2 reuses the control's real specifics into named‑evidence steps + a separate CSA test → owner completes only the true gaps.

In both: **the control is the checking, the test obtains and verifies the named evidence, and nothing is invented — unknowns are marked for the owner.**
